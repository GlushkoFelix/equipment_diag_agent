## 5. 接下来要做什么（按顺序）

### 第一步：后端先跑起来（M0 自检）
- 检查 `.env`、SQLite 迁移、检查点库、`models/bge-m3` 加载、`data/ai4i2020.csv` 可读。
- 运行后端，确认 `/health`、启动自检通过。
- 重新生成 `docs/openapi.json`，与 ARCH V1.2.0 逐字段对齐。

### 第二步：前端生成类型并对接
- 用 `docs/openapi.json` 生成 `frontend/src/api/schema.d.ts`。
- 前端先用 Mock 检查布局/状态矩阵，再切真实接口。
- 重点检查：SSE 原生重连、终态关闭、2s 轮询降级、`degraded + auto_review` 双标注、批量进度由 `counts` 计算。

### 第三步：联调关键链路（P0）
1. 单条表单诊断：提交 → SSE → 报告 → 导出。
2. CSV 单条与批量：预检、映射、批量进度、取消、导出。
3. 自然语言：部分缺失 → `clarification` → 补充 → 继续。
4. 对话：`draft` 首条只出抽取卡 → `/confirm` 创建诊断（RT-17 命中 200 复用）→ 202 后建流。
5. 人工中断：review 第 1 轮确认/补充/放弃；第 2 轮仅确认/放弃。
6. 超时与降级：全局 15s → `failed_timeout` 无报告；报告缺项 → `degraded`。
7. 批量低置信 → `degraded_review`；批量行不出现 `waiting_human/expired`。

### 第四步：测试与验收
- 开测试/验收窗口，用 `agent-browser` 做 E2E 截图与点击。
- 对照 PRD 附录 B 的 AC 用例逐条验收。
- 对照 ARCH 契约测试：每个端点成功 + 错误；SSE 事件 Schema；RT-17 200/202/409/422。
- 对照 DB：部分唯一索引、终态清指纹、事件 seq 唯一、批量计数守恒、会话删除保留。
- 重点回归 `P2-N1`：`terminal` 且 `diagnosis_id` 为空的会话不得再绑定新诊断；`/confirm` 只允许 `draft`。

### 第五步：修复与冻结
- 联调缺陷按“前端/后端/契约”分类修复；涉及契约变更先登记 ARCH §10.4。
- 全部 AC 通过后，冻结代码版本，进入演示/交付。
