P0-01 批量行与人工中断/超时未闭环
- 依据：§3.2.1 `csv_batch` → 批量调度器；§3.6 批量路径"每行独立会话执行单条诊断流程"；RT-08 低/中置信转 `review`；RT-16 挂起 30 分钟转 `expired`。
- 缺口：§2.5.4 与 §4.5.1 的 `batch_row.status` 只有 `pending/running/succeeded/degraded/failed/cancelled`，`batch_task.status` 只有 `queued/running/completed/partially_failed/failed/cancelled`，均无 `waiting_human`/`expired`；FR-IN-04 只定义"取消"，未定义行级人工中断、批量级超时、自动确认/跳过策略。
- 后果：任一低置信行会把任务永久停在 running；AC-IN-06（240 行 → completed，成功+降级+失败=240）、AC-EV-08（分母 240/200）、KPI-04（只排除 cancelled）均无法成立。
- 返修：二选一并写死——① 批量行不进入 review/clarification，低置信行按固定策略直接产出"待人工复核"的降级报告并继续；② 允许行级 `waiting_human`/`expired`，批量任务增加 `waiting`/`partially_completed`，并明确 KPI-04 分母是否排除。同步枚举、UI、AC。

P0-02 RT-17 幂等与批量独立行冲突，"输入指纹"未定义

- 冲突：批量中相同设备+相同特征的重复行（并发 2）会命中 RT-17，第二行复用第一行 `diagnosis_id`，导致 240 行 ≠ 240 次诊断，行级 trace/报告错位，KPI-04 分子分母失真；RT-17 未声明仅适用于单条入口。
- 另：`input_fingerprint` 未在 §3.5/§4.5 定义（哪些字段、是否含原文/设备/入口），AC-DG-15 无法独立执行。
- 返修：限定 RT-17 仅作用于 `csv_single/form/nl/chat`，批量与评测豁免；在 §3.5/§4.5.2 定义 `input_fingerprint` 的计算口径与存储；补"批量重复行各自生成诊断"用例。

P0-03 15s 熔断的 `degraded` 语义与报告、KPI 冲突
- 依据：§3.8 "触发 15s 熔断时输出已完成步骤、已得特征与'超时降级'说明，状态 degraded，不生成未经验证的结论"；§3.6 注"可从 parse_input/retrieve/diagnose/report 任一执行节点直接进入 degraded_finalize"。
- 冲突 1：§4.5.1 定义 `degraded` = "报告已产出但缺项标注"；熔断在 parse 时无诊断、无报告。
- 冲突 2：US-25/FR-RP-02 要求 8 要素全部非空；熔断降级无法满足。FR-RP-08 的 `degraded` 仅指"报告自检重试后仍缺项"。
- 冲突 3：KPI-04 分子为"成功（含降级）产出报告"，无报告的熔断被计为成功，指标虚高。
- 冲突 4：KPI-03 明确"降级样本不纳入正常时延统计"，且全文无降级率上限；大量 15s 熔断仍可使 KPI-03/04 全部通过。
- 缺口：附录 B 无 15s 熔断用例（parse/retrieve/diagnose/report 四个触发点均无）。
- 返修：拆分语义——`degraded` 仅表示"报告已产出但有缺项"；15s 熔断若发生在 report 之前，进入 `failed`（如 `TIMEOUT`）或新增 `timeout` 状态且不计入 KPI-04 分子；若发生在 report 阶段，按缺项降级。同步 §3.6/§3.8/§4.5.1/§2.5.7、KPI-03/04 口径，并补四个触发点的 AC。

P0-04 `expired` 的触发机制缺失，AC 依赖未定义配置
- 依据：RT-16、§3.7、§3.6 `expired` "挂起超时，释放资源"；未定义由后台定时器还是读/恢复时懒判定触发。

P0-05 §3.5 白名单与字段写入方自相矛盾
