## 二、P0 缺陷（必须修复后复评）

### P0-1 SSE 重连与轮询参数与冻结契约数值冲突（§4.10、§12.6）

- **UIUX 现状**：
  - §4.10 / §12.6："断线自动重连：1s、2s、4s、8s，上限 10s"；
  - §12.6："轮询降级……轮询间隔 3s；不伪造进度"。
- **契约要求**：
  - ARCH §8.3："重连：EventSource 自带；服务端 `retry: 3000`；**不手写重复建流**"；"失败降级：`onerror` 连续 3 次 → 关闭 SSE，改为**每 2s** `GET /diagnoses/{id}`；恢复后再建流"；
  - ARCH §6.5："EventSource 自动重连（retry=3000）"；ARCH 附录：`retry: 3000` 指示浏览器重连间隔；
  - HANDOFF §4-3："终态 `close()`；**3 次失败转 2s 轮询**"。
- **冲突**：UIUX 的"1/2/4/8 上限 10s"指数退避必须手写重建 EventSource，与"不手写重复建流"直接矛盾；轮询间隔 3s 与契约的 2s 冲突。前端实现无法同时满足两文档。
- **修复建议**：（a）按 ARCH 改为"采用 EventSource 原生重连（服务端 `retry=3000`）；连续 3 次失败切换为 2s 轮询 `GET /diagnoses/{id}`，恢复后再建流"，删除自定义退避；或（b）主张变更契约，同步修订 ARCH §6.5/§8.3 与 HANDOFF，并在 ARCH §10.4 登记偏差。建议按（a）修改。

### P0-2 `degraded + auto_review=true` 双标注口径缺漏（§6.3、§4.4、§4.6、§6.2）

- **契约要求**（属 ARCH P1-07 已裁定项，承接方含"前端双标注"）：
  - ARCH §4.2.2："若报告缺项进入 `degraded`，`auto_review` 仍为 true；**前端必须同时显示"缺项降级"和"待人工复核（批量模式）"**"；
  - ARCH §8.4："`degraded` 且 `auto_review=true` 时同时显示两种标签，**顺序：缺项降级 → 待人工复核**"；
  - HANDOFF §4-4 必须落地项："`degraded + auto_review` 双标注"。
- **UIUX 现状**：§6.3 仅规定"批量行同时满足缺项与低置信时同样取 `degraded`，不显示 `degraded_review` 状态"；§4.4/§4.6 覆盖表将"待人工复核"仅挂在 `degraded_review` 状态上；§6.2 虽列有"批量复核"徽标但无触发规则。既未承接"必须同时显示"的强制要求，且"不显示 `degraded_review` 状态"的措辞易被实现为**不显示待复核标识**，自动复核事实（持久化标志 `auto_review`）在"缺项优先"组合下会丢失。
- **修复建议**：§6.3 补充明确规则："批量行缺项与低置信同时成立时：状态枚举取 `degraded`；报告须同时展示'缺项降级'与'待人工复核（批量模式）'两种标注，顺序：缺项降级 → 待人工复核；不提供确认动作"；§4.6 行状态表同步补充该组合的显示口径（徽标 + 横幅）。

## 三、P1 缺陷

### P1-1 批量进度 `cancelled` 口径与 ARCH `progress` 字段语义冲突、未登记（§8.2）

- UIUX §8.2：已完成 = `succeeded + degraded + degraded_review + failed + failed_timeout`；"`cancelled` 不计入已完成（未执行）；与 KPI-04 分母口径一致"。
- ARCH §8.7："任务进度 = `completed_rows / total_rows`"；`BatchTaskSummary.completed_rows` = "终态行数（**含失败/取消**）"。
- 冲突：取消/超时后若前端直接渲染服务端 `progress`，将把 `cancelled` 计入进度，与 §8.2 不一致。
- 说明：UIUX 的不计入口径符合 PRD KPI-04（"不含 cancelled"）及本次审查重点预期，问题在跨文档未对齐。
- 修复建议：在 §8.2 注明"进度不使用服务端 `progress` 字段，由 `counts` 按本口径计算"，并在 §0.5 偏差登记说明中登记；同时推动 ARCH §8.7 口径对齐（或将 `completed_rows` 拆分为"终态行数"与"已执行行数"两个字段）。

### P1-2 评测页"待复核（`degraded_review`）计数"缺数据来源（§9.4）

- UIUX §9.4 统计块含"待复核 | `degraded_review` 数量 | `2 / 120`"。
- PRD §4.5.1 `eval_sample.status` 取值仅 `succeeded/degraded/failed/failed_timeout`，**无 `degraded_review`**；ARCH §4.2.1："eval 低置信 → 夹具自动确认，不做待复核（终态 `succeeded` 或 `degraded`）"。
- 仅 PRD §3.10.3.6 要求"评测报告须包含……`degraded`/`degraded_review` 计数"——基线内部存在矛盾。
- 影响：该卡数据来源未定义，可能恒为空转展示或无法取值。
- 修复建议：（a）若裁定 eval 不产生该计数，卡片改为显示 `0` 或 `N/A` 并注明"评测样本不做待复核"，同时登记基线矛盾；或（b）保留展示则先推动 PRD §4.5.1（`eval_sample.status`）、§3.10.3.6 与 ARCH §4.2.1 三方裁定后再实现。建议（a）+登记。

### P1-3 组件内写死色值、个别色值未令牌化（§10.12、§3.3、§2.12）

- §10.12 `DataTable`："行 Hover `#F2F7FB`"——该色值未纳入 §2.2.1/§2.2.2 或 §2.12 CSS 变量清单（仅出现在 §2.11 AntD 映射表），违反本文档 §0.3"颜色使用 Design Token，禁止组件内写死十六进制值"，且 §13.1 验收项"所有颜色来自 Design Token，无组件内写死色值"将无法通过。
- §3.3 工作台布局表：顶部栏写"`#1C2A36`"，应引用已有令牌 `--color-bg-header`。
- 修复建议：新增 `--color-row-hover: #F2F7FB`（或并入既有语义令牌）并登记进 §2.12 清单；§10.12/§3.3 改为引用 `var(--…)` 令牌。

- §7.6"会话建立"："进入页签创建草稿会话；**首次发送消息创建诊断记录并绑定会话**"（L1417）。

- §7.5"自然语言与抽取确认卡"只覆盖自然语言页签（文本域 120px），未声明对话页签共用。
- §3.1 信息架构、§3.2 页面流转图均无"抽取确认卡"节点。

**契约与基线要求**
- ARCH V1.2.0 §8.8："首条消息 `POST /chat/sessions/{id}/messages` **只返回抽取确认卡，不创建诊断**"；"用户在卡上修改并点击确认 → `POST /chat/sessions/{id}/confirm`（携带 `text` + `features`）；缺项允许提交，随后按 RT-02 进入 clarification"。
- ARCH §5.4.5：`draft` 会话首条消息返回 200、`diagnosis_id=null`、`extraction` 载荷；`active+clarification` 的自由文本"只返回补充卡，**不直接应用**"，用户确认后走 `resume`。
- PRD §2.5.8"抽取确认"："自然语言页签与对话页签**共用抽取确认卡**：列出 6 特征 + 设备标识、单位与置信提示；用户修改后提交，trace 记录'用户修正'"。
- UIUX §0.2 自述冲突规则："**接口/SSE 行为以 ARCH V1.2.0 为准**"。

**冲突性质**
1. 按 UIUX 实现，对话首条消息即创建诊断，与 ARCH 的 200/`diagnosis_id=null` 契约直接冲突，前端无法据此渲染确认卡，也无法实现"修改后提交并记录用户修正"。
2. UIUX 缺失 PRD §2.5.8 明确要求的"对话页签共用抽取确认卡"，属需求漏项，不依赖 ARCH 也成立。
3. PRD §2.5.8"会话建立"与 ARCH §8.8 本身存在基线分歧，UIUX 直接沿用 PRD 旧措辞且**未登记偏差**，违反本文档 §0.2 的冲突处理约定。

**修复建议（P0）**
1. §7.6"会话建立"改写为三步：进入页签创建 `draft` 会话 → 首条消息仅做抽取并返回确认卡（**不创建诊断**）→ 用户在卡上修改并确认后调 `confirm` 创建诊断（命中 RT-17 返回 200 复用已有，缺项按 RT-02 进入 clarification）。
2. §7.6"消息类型"补"抽取确认卡"；明确对话页签与自然语言页签共用同一卡片、同一校验与"用户修正"留痕。
3. §3.1 信息架构与 §3.2 页面流转图补"抽取确认卡（内嵌，非模态）"节点。
4. §0.5.1 新增 DEV-03，登记"PRD §2.5.8 会话建立（首条消息建诊断）vs ARCH V1.2.0 §8.8（确认后建诊断）"的分歧与本文档取值。
5. §13.2 追踪矩阵补 ARCH §5.4.5、§8.8 依据。

## 三、P1 缺陷（新增）

### P1-4 对话会话的 409 错误态未定义（§7.6、§4.10）

- ARCH §5.4.5 定义三种会话级拒绝：`review` 下自由文本 → 409 `CHAT_DECISION_REQUIRED`；`running` → 409 `DIAGNOSIS_STATE_CONFLICT`；`terminal` → 409 `CHAT_SESSION_CLOSED`（前端提示"新建对话"）。
- UIUX §7.6 未定义上述任一错误态的界面表现；§4.10 全局异常态也无对话相关条目。
- 修复：在 §7.6 增加错误态表（对应提示文案 + 下一步动作），并在 §4.10 补"会话终态"条目。

### P1-5 澄清中自由文本 → 补充卡 → 确认 → resume 链路未定义（§5.2、§7.6）

- ARCH §8.8 / §5.4.5：澄清中的自由文本"只返回补充卡，不直接改状态；用户确认后统一走 `resume`（decision=supplement，version 来自快照）"。
- UIUX §7.6 仅写"追问 | 使用内嵌卡片"，未说明对话中的自由文本回复如何转为补充卡、是否需要二次确认、如何携带 `version` 提交。
- 修复：在 §7.6 或 §5.2.5 补该链路；明确"未确认前不提交 resume、不改变状态"。

### P1-6 RT-17 去重命中后的前端行为未定义（§4、§7）

- ARCH §5.4.6/§5.4.5/§5.6.9：单条入口（含对话 confirm）命中 RT-17 时返回 **200 + 已有 `diagnosis_id` + `deduplicated=true`**，"前端直接打开已有诊断，不重复执行"。
- UIUX 全文无 RT-17/`deduplicated` 的处理口径（仅 §5.2.2、§5.3.7 有"重复提交"与版本幂等，语义不同）。
- 影响：前端可能把 200 当异常，或重复建流、重复渲染。
- 修复：在 §4.8 或 §7 增加"重复输入"状态行：复用已有诊断并载入右栏、不新建流、给出轻量提示；对话 confirm 同理。

## 四、P2 观察项

### P2-2 §4.7 历史查看的批量行表述需限定（§4.7）

- §4.7："历史加载批量行诊断时按 `degraded_review` 显示"（L877）。该句与 P0-2 的双标注规则存在被误读为"所有批量行诊断均按 degraded_review 显示"的风险（若源状态为 `degraded`+`auto_review=true`，应显示"缺项降级 → 待人工复核"）。
- 建议改为"历史加载 `status=degraded_review` 的批量行诊断时按 `degraded_review` 显示；`degraded + auto_review=true` 按 §4.6 双标注显示"。

### P2-3 §8.2 "与 KPI-04 分母口径一致"表述不精确（§8.2）

- ARCH §5.4.7：`success_rate = (succeeded+degraded+degraded_review) / (total_rows − cancelled)`；UIUX 进度为"已完成 / 总行数"。
- 两者在"`cancelled` 不计入"上一致，但分母定义不同。建议改为"`cancelled` 不计入已完成，与 KPI-04 对 `cancelled` 的处理一致；进度分母为总行数，取消后按 §4.5 冻结"。

## 六、残留 P2 观察项（不阻塞冻结）
